# Átrio v0.1 — Implementation Roadmap

**Status:** Sequência de implementação proposta após aprovação da Architecture Specification  
**Architecture Spec:** `docs/superpowers/specs/2026-10-02-atrio-architecture-design.md`  
**Execution model:** planos independentes, TDD, commits frequentes, review gate entre planos.

## Objetivo

Implementar o MVP v0.1 do Átrio em incrementos que permaneçam compiláveis, testáveis e demonstráveis. Cada plano abaixo entrega capacidade real e fecha um conjunto coerente de riscos antes do próximo.

## Plan 01 — Foundation & Platform Baseline

**Outcome:** repositório `atrio` inicializado com backend .NET 10, frontend React 19/TypeScript/Vite, PostgreSQL, Clean Architecture, architecture tests, OpenAPI/ProblemDetails, health/version endpoints, Docker development stack and CI.

**Demonstrable result:** `docker compose up` inicia web, API e PostgreSQL; `/health/live`, `/health/ready` e `/api/v1/system/version` funcionam; backend/frontend tests passam.

---

## Plan 02 — Identity & Access

**Outcome:** bootstrap administrator, `Person`/`UserAccount`, roles, invitations, login/logout, server-side sessions, CSRF, forgot/reset password, password change, reauthentication, account disable/reactivate and security-version revocation.

**Critical gates:**
- nenhum bearer token em localStorage;
- sessão desativada deixa de funcionar imediatamente;
- tokens hashed/single-use;
- neutral responses against account enumeration;
- Administrator-sensitive operations require recent reauthentication.

**Demonstrable result:** instalação limpa cria primeiro admin com bootstrap token; admin convida Guardian/Teacher; usuário ativa conta, entra, sai, recupera senha e tem sessões corretamente revogadas.

---

## Plan 03 — People, Families & Academics

**Outcome:** institution settings, People, Families, Students, GuardianFamily, TeacherContact, AcademicPeriod, Classes, Subjects, ClassSubject, StudentEnrollment and TeachingAssignment.

**Critical gates:**
- Student belongs to exactly one Family;
- overlapping GuardianFamily/Enrollment/TeachingAssignment ranges are rejected;
- at most one Active and one Draft AcademicPeriod;
- roles do not substitute contextual relationships.

**Demonstrable result:** Admin configures the institution and the current academic structure entirely through API/UI without direct database manipulation.

---

## Plan 04 — Secure File Pipeline

**Outcome:** private upload/download, quarantine, validation, file metadata, filesystem implementation behind `IFileStorage`, upload progress contract, authorization, Range streaming and orphan cleanup.

**Critical gates:**
- max 25 MB per file;
- whitelist only;
- invalid/mismatched file signatures rejected;
- no direct storage paths/URLs;
- only `Available` files can be served/attached.

**Demonstrable result:** authorized user uploads PDF/audio/image/Office files; invalid files are rejected; authorized download supports media streaming; unauthorized IDs do not reveal files.

---

## Plan 05 — Publications Editorial Core

**Outcome:** Publication aggregate, types/contexts, targets, materials, StudentPublicationDetail, Draft autosave API, Publish/Unpublish/Archive, optimistic concurrency, audience materialization and PublicationStudentAccess.

**Critical gates:**
- Teacher can publish only in active TeachingAssignment contexts;
- StudentDetails only for eligible students;
- Guardian access grants persist historically;
- published content cannot be permanently deleted;
- publication lifecycle commands are idempotent.

**Demonstrable result:** Teacher creates a multi-class Music Presentation with materials and individual student instructions, publishes it and the database materializes correct student access.

---

## Plan 06 — Family & Teacher Experiences

**Outcome:** production-quality React experiences for Minha Família and Professor: Home, Agenda, Meus filhos, Minhas turmas, Minhas publicações, publication details, search/filtering and responsive/mobile UX.

**Critical gates:**
- one family never receives another family’s StudentDetails;
- multi-child publication appears once;
- child filters adapt details without duplication;
- teacher roster is limited to authorized classes;
- deep links survive login.

**Demonstrable result:** the primary end-to-end product journey works on desktop and mobile without email dependency.

---

## Plan 07 — Notifications & Transactional Outbox

**Outcome:** NotificationOccurrence, NotificationDelivery, Outbox, background processing, email templates, deduplication, retry/backoff and development Mailpit.

**Critical gates:**
- publication transaction does not wait for SMTP;
- one account gets at most one email per occurrence/channel;
- SMTP outage keeps business transaction committed and delivery retryable;
- disabled/not-eligible accounts do not receive delivery.

**Demonstrable result:** publishing creates notification records and an email arrives in Mailpit; SMTP failure can be recovered without re-publishing.

---

## Plan 08 — Administration, Search & Audit

**Outcome:** Admin Home, global search, account/access management, bulk invites, institutional/ClassGeneral publications, pinning, publication administration, immutable audit queries and PostgreSQL tolerant search.

**Critical gates:**
- admin actions requiring reauth enforce it server-side;
- institutional audiences are derived, not manually maintained;
- private StudentDetails never leak into general search;
- audit writes are transactionally coupled to sensitive commands.

**Demonstrable result:** the institution can operate the v0.1 through its Admin interface, including onboarding the initial population.

---

## Plan 09 — Production Hardening & Go-Live

**Outcome:** production Compose, Caddy/TLS, runtime/migrator database roles, migration job, backup/restore runbook, release/versioning, log rotation, health diagnostics, security headers, rate limits, dependency/security scans and go-live threat-model checklist.

**Critical gates:**
- only ports 80/443 publicly exposed;
- PostgreSQL/API internal only;
- HTTPS real;
- restore tested on clean environment;
- negative authorization suite and E2E critical journeys green;
- secrets absent from Git/logs.

**Demonstrable result:** a tagged release can be deployed on the initial Windows host, backed up, restored and later moved to Linux/VPS without application changes.

---

# Global sequence gates

Before advancing from one plan to the next:

1. all tests introduced by the plan pass;
2. backend and frontend build pass;
3. architecture tests pass;
4. Docker smoke tests relevant to that plan pass;
5. documentation/runbook affected by the plan is updated;
6. branch is reviewed before merge;
7. subsequent work starts from updated `main`.

# Non-negotiable implementation rules

- TDD for domain rules and bug fixes.
- Authorization is never delegated to React.
- PostgreSQL integration behavior is tested against PostgreSQL, not EF Core InMemory.
- No `GenericRepository<T>`.
- No RabbitMQ/Redis/Kubernetes/Elasticsearch unless a later approved architecture change explicitly introduces them.
- No permanent public file URLs.
- No database-to-database coupling with BiblioFlux.
- No implementation plan may silently expand the Product Design scope.
